# 設計方針レビューとロードマップ（日本語）

最終更新: run 52 相当。外部レビュー（別モデルによる設計相談）を反映した現行方針。
対象ブランチ: `feature/gpu-hybrid-m3-m4`。

## 0. 結論（要約）

1. **製品路線は x264/x265 フォーク＋GPU 解析アダプタへ寄せる**。自作 aeg は
   「GPU 解析エンジンの参照実装・決定性テストベッド」として残す。
2. aeg にこれ以上コーデック機能（4:2:2、12bit、lossless CABAC 等）を積むより、
   GPU 側の**前処理・先読み・ME 候補生成**をフォークに注入する方が、画質・機能・
   互換性のリスクが小さい。
3. GPU は**候補生成と枝刈りヒント**に限定し、最終 RDO・CABAC・デブロック・SAO は
   CPU 本家のまま。GPU 結果は従来候補と併評価し、枝刈りは安全マージン付き。
4. 同期は**フレームまたは miniGOP 単位**。MB/CTU 単位の往復は禁止。
5. 新しいゲートは「往復回数/フレーム」「ヒント転送 KB/frame」で定義する。
6. 上限測定（x265 analysis save/load）では、同一ビットストリームのまま
   **2.37 s → 1.48 s（約 1.6x）**。GPU 実装前にこの上限を確認する。

## 1. 外部レビューの採用 / 不採用

| 指摘 | 判断 | 理由 |
|---|---|---|
| CABAC / RDO / intra / MV コストは GPU に載せにくい | **採用** | ビット単位逐次・状態依存・隣接再構成依存。1080p の波面並列は数十並列で頭打ち |
| 前処理・先読み・SAD/SATD・補間は載せやすい | **採用** | 画素演算が独立。既存 aeg の lowres batch / SAD/SATD と一致 |
| x264/x265 をフォークし、RC/psy/AQ/MB-tree/bitstream は触らない | **採用（製品路線）** | 画質・機能・互換性の再実装リスクを避ける。GPL を許容する |
| GPU は候補生成、CPU が最終判定 | **採用** | 画質同等を担保し、GPU は枝刈りヒントに限定 |
| フレーム/miniGOP 同期 | **採用** | 起動・転送オーバーヘッドを償却 |
| 全機能 CPU フォールバック | **採用** | GPU 無し・未対応機能で本家パスをそのまま使う |
| MV 予測依存を上位レベル/前回反復で切る | **採用** | 最終予測値で CPU が再評価。x264 OpenCL lookahead と同じ回避法 |
| 再構成依存を原画探索＋CPU リファインで切る | **採用** | 低ビットレートでは再構成アップロードモードを追加 |
| 階層型網羅探索（粗→上位候補周辺） | **採用** | hex/umh より取りこぼしが少ない。GPU の余力を使う |
| 先読みコスト定義を本家と一致 | **採用** | RC/シーンチェンジ/MB-tree のスケール依存。ここはビット一致目標 |
| 整数演算・同コスト規則固定 | **採用** | CPU 参照・ベンダー間一致と自動テスト |
| ページロック＋非同期、内蔵 GPU ゼロコピー | **採用** | 転送削減。ヒントは上位 1〜2 候補に限定 |
| CLI/API は libx264/libx265 互換＋GPU オプション | **採用** | ffmpeg から差し替え可能にする |
| CUDA SDK をリンクせず PTX＋ドライバ API | **採用** | 配布容易性。既存 aeg の NVRTC/ドライバ動的ロードと同方向 |
| いま aeg を捨てて直ちにフォークへ移行 | **条件付き採用** | まず上限測定とアダプタ設計。aeg は参照実装として維持 |
| GPU に RC/エントロピー/デブロックを載せる | **不採用** | 本家の決定性・画質を壊す。アムダール上限も悪化 |
| MB/CTU 単位の同期 | **不採用** | 転送・起動で必ず負ける |

## 2. aeg vs x264/x265 フォーク

| 観点 | 現行 aeg（自作） | x264/x265 フォーク＋GPU アダプタ |
|---|---|---|
| 画質 | x264 medium に対し BD-rate 10–20% 差が残る | 本家と同等。GPU は候補追加で改善余地 |
| 機能 | 4:2:0 8/10bit、CABAC/CAVLC、B、CQM、lossless 8bit まで。4:2:2/4:4:4/12bit 未完 | 本家の全機能（4:2:2/4:4:4、12bit、lossless、AQ/psy/CQM、コンテナ連携） |
| 互換性 | Annex-B / 一部コンテナ。libavcodec 互換なし | libx264/libx265 API・CLI 互換。ffmpeg 差し替え可 |
| 速度 | CPU 実装。GPU はステージ単位で部分的 | 本家 CPU 最適化＋GPU 候補生成。x264 1.2–1.5x、x265 1.5–2x が現実的目標 |
| 工数 | コーデック機能を一つずつ再実装（高） | アダプタ＋GPU 解析エンジン（中〜高） |
| リスク | 画質・機能の再実装リスク、互換性検証コスト | GPL、フォーク追従、GPU 枝刈りの BD-rate 検証 |
| 決定性テスト | 348 backend + CPU 参照 + バイト一致が資産 | 本家とのビット一致＋候補注入の差分テストが必要 |
| 判断 | **参照実装・テストベッドとして維持** | **製品路線として採用** |

## 3. aeg 資産の再利用判定

| 資産 | フォーク路線での扱い | 理由 |
|---|---|---|
| backend 抽象（CUDA/OpenCL/CPU） | **再利用（解析エンジン層へ移植）** | 3 層構成の (1) 計算バックエンド層にそのまま使える |
| CPU 参照・決定性テスト（backend_check 348） | **再利用** | GPU カーネルの基準。フォーク側でも解析カーネルの一致試験に使う |
| lowres バッチ探索 | **再利用** | 先読み・階層 ME の粗探索に直結 |
| 固定小数点 mbtree | **一部再利用（凍結）** | 発想は使えるが、本家 MB-tree のコスト定義とスケールを合わせる必要 |
| deblock persistent 参照 | **不要（参考のみ）** | フォークでは deblock は CPU 本家。デバイス deblock は路線外 |
| `--mux` | **再利用可** | 薄い ffmpeg ラッパ。フォーク CLI でも同じ仕組みが使える |
| lossless I_PCM | **参考（本家を使う）** | フォークでは本家 lossless を使う。aeg の実装はテスト資産 |
| 12bit experimental | **不要** | 本家 12bit を使う |
| CQM / weighted B / open-GOP | **本家機能を使う** | 再実装しない |
| `--mv-hints`（今回のプロトタイプ） | **アダプタ interface の雛形** | 外部候補 MV 配列を注入する形を先に決める |

## 4. M-1 ゲートの再定義案

旧ゲート（自作エンコーダ内）:
- 転送 ≤4 MB/pic
- 呼び出し ≤20 calls/pic

新ゲート（フォーク＋GPU 解析）:

| 項目 | 目標 |
|---|---:|
| ホスト↔GPU の往復回数 | **≤2 / frame**（前処理＋先読み、ME ヒント） |
| 追加往復（再構成アップロード時） | ≤1 / miniGOP |
| カーネル起動回数 | ≤8 / frame（バッチ化。MB 単位禁止） |
| ヒント転送量 | **≤128 KB / frame（1080p）**、≤512 KB / frame（4K） |
| フレーム本体転送 | 入力 1 回 + 参照 1 回 / miniGOP（ページロック＋非同期） |
| 同期点 | フレーム末尾または miniGOP 末尾のみ |
| フォールバック | GPU 無し/遅い場合は起動時計測で自動 OFF |

1080p の根拠: 8,160 MB × 16 B/MB（MV 2 + cost 4 + flags）≈ 128 KB。
ヒントは上位 1〜2 候補に限定すれば 64 KB/frame 以下にできる。

## 5. 上限測定（実測）

x265 2.6 の analysis save/load を使用。cockL 240f、640x352、CRF 27、preset medium。

| モード | 時間 | 出力 | 備考 |
|---|---:|---:|---|
| save（通常解析） | 2.37 s | 168,530 B | analysis を保存 |
| load refine 0 | 1.48 s | 168,530 B | 同一ビットストリーム |
| load refine 3 + refine-mv | 1.53 s | 168,530 B | 同一ビットストリーム |

- **約 1.6x** の速度上限（解析再利用のみ、画質同一）。
- これは GPU 実装の上限測定であり、GPU そのものの測定ではない。
- x264 の ESA MV 注入は改造が必要なため、今回は設計メモのみ（未実装）。
- 参考: aeg の lowres batch は既に CPU/GPU でバイト一致しており、
  同種の「解析再利用」をフォーク側へ移植する価値がある。

## 6. パイプライン（採用）

```
入力
  → [GPU] 前処理（縮小・ノイズ/シーンチェンジ統計）
  → [GPU] 先読み（低解像度 ME・コスト・AQ 統計）
  → [CPU] フレームタイプ / MB-tree / CU-tree / RC
  → [GPU] フル解像度 ME 候補 + intra/CU 候補（開ループ、原画）
  → [CPU] 本エンコード（RDO / 変換量子化 / CABAC / deblock / SAO）
  → 出力
```

## 7. 今回のコード前進

- `--mv-hints <file>` を追加（プロトタイプ）。
  - 形式: MB ラスタ順に `mv_x mv_y` の整数 2 個 × MB 数。
  - P スライスの 16x16 ME の **seed** として使用。
  - 既定（未指定）は完全に従来経路。1080p 12f は 197,721 バイトのまま。
  - これは「外部候補 MV 配列を注入する」アダプタ interface の雛形。
- 本格的な候補配列（上位 K、コスト、パーティション）はフォーク側の
  `x264_me_search_ref()` / `Search::singleMotionEstimation` に渡す形へ拡張する。

## 8. ロードマップ

1. **M-8A 上限測定の完走**: x265 analysis reuse の複数 CRF、x264 ESA 注入の改造可否。
2. **M-8B 解析エンジン層**: aeg backend を移植し、低解像度 ME / SAD/SATD / intra 候補を
   CPU 参照付きで実装。
3. **M-8C x264 アダプタ**: `slicetype.c` / `me.c` に候補 MV 配列を注入。
4. **M-8D x265 アダプタ**: `slicetype.cpp` / `Search::singleMotionEstimation`。
5. **M-8E 画質・速度ゲート**: BD-rate PSNR/SSIM/VMAF と fps のパレートで判定。
6. **M-8F GPU 前提プリセット**と自動フォールバック。

## 9. 目標とリスク

- x264 medium 前後: 先読み+ME が 3〜5 割。理論上限 1.4〜2x、現実目標 **1.2〜1.5x**。
- x265: RDO 過半。枝刈りが効くため **1.5〜2x** を狙う。
- 多コア CPU＋非力 GPU では逆転し得る。起動時計測で GPU 経路を自動無効化。
- 「同等以上」は全条件勝利ではなく、**速度×画質のパレート曲線**で判定する。
