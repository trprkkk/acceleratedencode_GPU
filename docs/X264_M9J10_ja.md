## M-9J10 1080p クラッシュ切り分け（タイムボックス）

### 1. `-b cpu`（GPU 不使用）
- **成功**。1080p 120f の生成 **8.0 s（66.7 ms/frame）**。
- 出力 23.5 MB。
- ツール側の YUV 読み込み・低解像度プレーン・ヒント配列は正常。

### 2. 解像度の境界（`-b cuda`）
| 解像度 | 結果 |
|---|---|
| 640x352 | 成功 |
| 1280x720（n=2） | **成功** |
| 1920x1080（n=1） | **成功**（フレーム0のみ） |
| 1920x1080（n=2） | **SIGSEGV**（フレーム1） |

### 3. 原因の絞り込み
- 1920x1080 のフレーム1で、`cuda_me_batch` の
  `memcpy(pin, ref - AEG_PAD*stride - AEG_PAD, 253952)` が落ちる。
- 送信元 `ref` は 2.28 MB の `calloc` 領域。
- 1280x720 は 1.0 MB 程度で成功。
- **約 2 MB を超えるホスト領域**が境界。
- 1 MB チャンク、pinned staging（`cuMemAllocHost`）を試しても
  `memcpy` 時点で落ちるため、コピー API ではなく
  **ホスト側バッファの確保/参照**が原因。
- 低解像度プレーンを無効化しても同じ。
- 帯を 4→1 MB 行にしても同じ。

### 4. 4/4 化
- treeL のスキップ判定は未実装。
- 640p slow / limit:4 は 3/4 のまま。

### 5. 判定

| 項目 | 結果 |
|---|---|
| 1080p が動くか | **フレーム0のみ。フレーム1で SIGSEGV** |
| 境界 | **1280x720 成功 / 1920x1080 n=2 失敗** |
| 原因 | 2 MB 超ホストバッファの `memcpy` |
| 1080p E2E | **未測定** |
| 1080p 生成（CPU） | **8.0 s / 120f（66.7 ms/frame）** |
| 640p 4/4 | **未達（3/4）** |
| BD-rate | PASS（640p slow/limit:4） |

### 6. 次
- `src`/`ref` を **固定長の小ブロック（例: 512 KB）に分割**し、
  フレームを分割して `me_batch` を呼ぶ（バッファ全体を確保しない）。
- または `AEG_PAD` を 32→16 に下げて 1080p のホスト領域を削減。
- 1080p は CPU フォールバック 66.7 ms/frame なので、
  GPU が通れば 10 ms/frame 前後が期待できる。
